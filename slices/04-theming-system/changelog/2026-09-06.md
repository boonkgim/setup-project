## The `eslint.config.mjs` heredoc was destroying an earlier slice's work

The worst finding, and the one with the widest blast radius. This slice's block is the only
whole-file heredoc that overwrites a file an earlier slice wrote, and it was written as though
Slice 1 had left a plain three-config file. Slice 1 in fact leaves a `reactVersion` block —
`eslint-plugin-react` defaults to `version: "detect"`, whose detection path calls
`context.getFilename()`, removed in ESLint 10 — without which every rule `eslint-config-next`
contributes throws before a line is linted. Writing this slice's block verbatim takes `lint`
from green to a crash, and the slice's own gate row (`lint` unchanged) is what would catch it,
several steps later, with no clue as to why.

The block now carries the merge and, more importantly, says in prose that it *is* a merge and
that the existing file must be read first. Generalised deliberately: the next thing Slice 1
leaves in that file will not be a React version, so an instruction to carry across "whatever
Slice 1 actually left" outlives an instruction naming this particular workaround.

## `--font-heading` was missing from the mapping block

The prose named it — "new in `base-nova`, `CardTitle` uses it" — and the `@theme inline` heredoc
below did not contain the line. Following the block as written leaves `font-heading` unresolved,
so every `CardTitle` renders in the UA font while the rest of the page is correctly Geist. It
looks like a design choice, which is why nothing catches it: the theme test does not fail (the
mapping it would check is the thing that is absent), the build is green, and the page is
otherwise right. Added the line, and rewrote the prose to name the check that actually detects
it — the computed `fontFamily` of a rendered `CardTitle`, not a glance at the page.

Confirmed the failure is live rather than theoretical: 4.21's "Updating fonts" pass emits
`--font-sans: var(--font-sans)`, a token pointing at itself, exactly as the slice documented.
It also leaves `--font-mono: var(--font-geist-mono)` on the scaffold's old variable name, which
the prose had not mentioned; that half breaks the moment `layout.tsx` renames the variable, and
it is the second reason the `-src` rename is applied to both calls rather than one.

## The token blocks contradicted the paragraph above them

`--destructive-foreground` was still in both `theme.css` blocks and
`--color-destructive-foreground` in the `@theme inline` block, while the prose four lines up
told the reader to check whether the CLI still maps it and, if not, to add nothing. It does not,
at 4.21 — `base-nova`'s destructive variant is `bg-destructive/10 text-destructive` and needs no
foreground token. Removed from all three places so the blocks and the prose say the same thing.
A stale addition here is cheap in isolation and expensive as precedent: it is exactly the
"entry the next reader has to explain" the paragraph warns against.

## Note on driving the gate in a browser

Screenshot pixel coordinates are scaled relative to the page's CSS coordinates, so clicking a
control at the coordinates read off a screenshot can miss it silently — the page simply does not
change, which reads like a broken toggle. Resolve the element with `read_page` and click by
`ref`. Worth knowing for every slice whose gate has a `browser` row, not just this one.

## Round 2 passed unchanged; one production-gate row sharpened

Nothing in the production half failed, and the `__name` shim did its job on the real Worker:
`document.documentElement.style.colorScheme` was set, which is the line after the
`__name(k2, "k2")` call, and `domInteractive` landed before `first-contentful-paint`.

The one correction is to the cache row. It said a hard reload with the cache disabled was needed
"otherwise you are reading your own browser cache from the `pnpm preview` run" — but preview
serves from `localhost:8788`, a different origin, which can never be the source of a stale hit
on the deployed URL. The reasoning was wrong even though the advice was harmless. The cache that
can actually mislead you is the deployed origin's own, from a previous deploy, and the precise
way to defeat it is to re-fetch the stylesheet and the font with `cache: "no-store"` and read the
status and byte count back. That also turns the row from something judged by eye into something
with a number attached.

## The slice wrote a skill and never pointed `CLAUDE.md` at it

Slice 2 established the convention: when a layer gains a skill, `CLAUDE.md`'s entry for that
package gains a pointer to it, so the rule an agent is most likely to break is one file away
rather than restated inline. Slice 4 writes `project-web` — the skill carrying the theme
contract, which is the single most breakable rule in the repo — and left `CLAUDE.md`'s
`apps/web` line as the bare one-liner `create-next-app` justified. A skill nothing points at is
a skill that gets found by accident.

Added a `## The package map` section in the same shape as Slice 2's, with the same reasoning for
why the pointer and not the rule itself goes in `CLAUDE.md`.
