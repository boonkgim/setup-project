# Preflight, and the account question this slice used to ask

## The buried probe

`wrangler whoami` was in this file already — as an inline comment beside the
`CLOUDFLARE_ACCOUNT_ID=` heredoc, roughly step fifteen. Everything the run needed to know about
Cloudflare was therefore discoverable at step fifteen and unknown at step two, where the skill
decided whether to put the question to the user. It got asked instead.

## What changed

A `## Preflight` block now opens the slice with that one command, and a `USER-SETUP.md` carries
the signup link and the browser login. Two claims are stated where the decision is made:

- **A non-zero exit means logged out.** That is the probe's answer, not an error to retry.
- **`whoami` prints every account with its id.** So *whether* the login carries more than one is
  never a question — only *which row to use* is, and that is the operator's call because
  wrangler refuses to guess in non-interactive mode. Verified against wrangler 4.129.0, which
  prints the account table as part of normal `whoami` output.

The catalog's `Needs` entry for this slice gains the same correction: do not ask whether either
is true.

Neither blocks the local half. The slice builds, gates and commits with Round 2 deferred, which
the preflight block now says out loud — previously a missing account stranded the run at the
production gate with the local half already committed, which is the failure §2 had always
described and never given anyone the means to avoid.

# Pins re-resolved, and the vendor guide that stopped documenting this path

Second change today, from an actual build of the slice. Round 1 went green with no step
failing, so everything below is drift caught by §3 research rather than by a broken gate.

## Versions re-resolved

| Claim | Said | Now | How it was checked |
| ----- | ---- | --- | ------------------ |
| `create-next-app` | 16.3.3 | **16.3.4** | `--help` re-read: every flag the block passes still exists and still means what it says |
| `@opennextjs/cloudflare` | 1.20.4 | **1.20.6** | peer range unchanged: `next: ">=15.5.24 <16 \|\| >=16.3.3"`, `wrangler: "^4.125.0"` |
| Next scaffolded | 16.3.3, "the exact bottom edge" | **16.3.4**, one patch above it | the pair still agrees; checking the pair rather than either half is what the rule was for |
| `compatibility_date` | `2026-08-28` | **`2026-09-03`** | `wrangler@4.129.0` depends on `workerd@1.20260903.1` |
| Vitest in the `type: "module"` prose | 4 | **5** | `vitest@latest` is 5.0.0; the ESM-under-CommonJS warning and its fix are unchanged |

The `compatibility_date` line now says to re-derive it from `npm view wrangler@<version>
dependencies` every time, because it is the one value in this slice that is wrong on a
schedule. Note the gap it exposes: the build ran on 2026-09-06 and the correct date was
2026-09-03. Reaching for the calendar would have produced a date workerd cannot implement.

## Still true, checked rather than assumed

- **The `eslint-plugin-react` workaround is still load-bearing.** `7.37.5` remains the latest
  published and still peers `eslint: "^3 || … || ^9.7"`. `pnpm peers check` against the
  catalog's ESLint 10 named all three of the transitive plugins the REFERENCE predicts —
  `eslint-plugin-import`, `eslint-plugin-jsx-a11y`, `eslint-plugin-react`. With
  `settings.react.version` declared, `lint` passes and no rule throws.
- **No deprecations** across the eleven packages this slice touches (`npm view <pkg>
  deprecated`, empty for all).
- **The nested `pnpm-workspace.yaml` had the real-entries shape** — `sharp: false`,
  `unrs-resolver: false`, not the `set this to true or false` placeholders. The REFERENCE
  already says not to bother matching the version because deleting the file is the whole fix
  either way; that held.
- **`wrangler.jsonc` survived prettier untouched**, confirming the heredoc is still stored in
  post-prettier form.

## The finding worth more than the pins

Cloudflare's framework guide for Next.js on Workers no longer documents OpenNext at all — it
documents **vinext**, and relegates OpenNext to a row about applications that "cannot yet
migrate". A new paragraph in the REFERENCE records this with the two checks that distinguish
vendor steering from actual deprecation (vinext is `1.0.0-beta.9`; OpenNext shipped four days
before this was written), and says to re-run them rather than inherit the verdict. The
`## Sources` entry for that guide is kept but marked as no longer sourcing the config, since
re-reading it is how the next person learns the answer has flipped.

This is the kind of drift the slice's own gates cannot catch: every command passes, the page
renders, and the stack is still quietly diverging from what the vendor recommends.

## Round 2: the first `workers.dev` load is a false negative

The deploy succeeded — `Deployed cc4-test-web triggers`, a version id, all three bindings
listed — and the URL then served Cloudflare's own branded **"There is nothing here yet"** page.
Styled HTML, arriving in place of the app, immediately after a deploy that reported success.
It reads exactly like a broken build.

It is route propagation on a `workers.dev` subdomain being served for the first time. `curl`
returned 200 on the very next attempt. The browser kept showing the placeholder after that,
because it had cached it — so the same false negative fires twice, once on the network and once
in the browser.

The REFERENCE's production gate now carries the poll loop and the hard-reload instruction, plus
the sentence that does the real work: **`wrangler` has already told you it worked.** An agent
that treats one look at the page as the gate's answer will start debugging a deploy that is
fine, and everything it "fixes" will be a change to working code.

Worth stating because it is invisible to every other check in this slice — `preview` under
local workerd never shows it, since there is no route to propagate.
