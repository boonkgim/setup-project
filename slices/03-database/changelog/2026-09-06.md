# Preflight, and the Neon steps that were never the agent's

## What changed

A `## Preflight` block probes the two prerequisites, and a `USER-SETUP.md` carries what a person
has to do about them.

The probes are deliberately different in kind. `docker info --format '{{.ServerVersion}}'`
answers *is the daemon running*, which `which docker` does not — installed-but-stopped and
absent are different problems with different fixes, and this slice's local gate fails
identically on both. The Neon side probes for a `DATABASE_URL` already on the machine rather
than for an account, because there is no command that can see a Neon project.

**The rounds they block are not the same, and the slice now says so.** Docker blocks Round 1;
the Neon project blocks Round 2 only. The infrastructure half — `packages/db`, its migrations
and its round-trip integration test — needs nothing hosted, so it is built, gated and committed
before Neon exists.

## Moved out of the REFERENCE

The create-project prose left this file for `USER-SETUP.md`: the "Enable Neon Auth" toggle that
must stay off, and how to tell the pooled host from the direct one. Both are things a person does
in a browser form, and REFERENCE.md is now strictly what an agent can execute. What remains here
is a pointer.

The two claims themselves are unchanged and still worth their space in the user's file: Neon Auth
provisions competing auth tables that slice 06's Better Auth schema would then sit beside, and
the pooled host is identifiable by `-pooler` in its name — the fastest check that the string in
hand is the direct one Hyperdrive wants.
