# Preflight, and the Neon steps that were never the agent's

## What changed

A `## Preflight` block probes the two prerequisites, and a `USER-SETUP.md` carries what a person
has to do about them.

The probes are deliberately different in kind. `docker info --format '{{.ServerVersion}}'`
answers _is the daemon running_, which `which docker` does not — installed-but-stopped and
absent are different problems with different fixes, and this slice's local gate fails
identically on both. The Neon side probes for a `DATABASE_URL` already on the machine rather
than for an account, because there is no command that can see a Neon project.

**The rounds they block are not the same, and the slice now says so.** Docker blocks Round 1;
the Neon project blocks Round 2 only. The infrastructure half — `packages/db`, its migrations
and its round-trip integration test — needs nothing hosted, so it is built, gated and committed
before Neon exists.

## Moved out of the REFERENCE

The create-project prose left this file for `USER-SETUP.md`: the "Enable Neon Auth" toggle that
must stay off, and how to tell the pooled host from the direct one. Both are things a person does
in a browser form, and REFERENCE.md is now strictly what an agent can execute. What remains here
is a pointer.

The two claims themselves are unchanged and still worth their space in the user's file: Neon Auth
provisions competing auth tables that slice 06's Better Auth schema would then sit beside, and
the pooled host is identifiable by `-pooler` in its name — the fastest check that the string in
hand is the direct one Hyperdrive wants.

# Renumbering leftovers, and a gate row that carried someone else's number

First recorded build of this slice through the three-round loop. Round 1 passed without a
single block needing a fix, so what follows is corrections to what the REFERENCE _said_, not
to what it does.

## Six cross-references pointed at this slice instead of the GraphQL one

The REFERENCE read "Slice 3's Worker currently answers `health` out of thin air", "configured
here and not in Slice 3", "the integration test which Slice 3 had no way to write", "already
satisfied by Slice 3's config", "the production page from Slice 3", and "Slice 3 stopped owning
that file whole". Every one of them means **the GraphQL slice, 2**. Read literally they are
self-referential — this file _is_ slice 3 — and the two that matter operationally are actively
misleading: a reader looking for where `compatibility_date` and the `docs-check.ignore` entry
came from is sent to the slice they are standing in rather than the one that wrote them.

These are fossils of the merge the catalog describes, where the old "API shell" and "One SDL"
slices became one and the numbering closed up behind them. The prose was renumbered; its
internal citations were not. Corrected to Slice 2 throughout.

Worth generalising: a slice that cites another by number is making a claim that breaks silently
under renumbering, and nothing in the loop checks it. `docs:check` compares code blocks against
the repo and never reads the prose between them.

## The unit-test row asserted a number this slice does not produce

The Round 1 table demanded `Tests 19 passed` from `pnpm test:unit`, annotated "unchanged". Both
halves cannot be true at once: if the count is unchanged, it is whatever the earlier slices left,
and this slice has no standing to name it. The repo it was built in this time had 17.

The number was also just wrong, which is the visible symptom of the real defect — §7's test
("would this sentence still be true in a repo with a different name, owner and account?") says a
count the slice does not itself create belongs in the project's doc, never here. Replaced with
**"unchanged from slice 2 — this slice adds no unit tests"**, which is checkable in any repo.

`Tests 2 passed` on `test:integration` stays a number, and should: this slice creates both tests,
so 2 is a property of the procedure. That is the line between the two cases.

## A drift the loop caught, working as designed

`pnpm docs:check` flagged `packages/db/src/client.int.test.ts`. The cause was the executing agent
collapsing a `.select().from().where()` chain onto one line while transcribing the heredoc; at
four spaces of indent that line is 80 characters, one over the repo's print width, so prettier
breaks it and the REFERENCE's multiline form was right all along. Doc correct, repo wrong,
`prettier --write` settled it — which is exactly the "decide which side is wrong" case §7
describes, resolved against the doc for once.

## Round 2, same day: the pooling toggle cannot be read, only verified

Driving the Neon Connect dialog through the browser tools surfaced something the REFERENCE had
no way to know when it was written by hand: **the pooling switch reports the accessible name
`"on"` in both states.** A scoped read of the element returns `switch "on"` before the click and
`switch "on"` after it, so the UI cannot confirm which endpoint you are about to copy.

That matters more here than a cosmetic a11y bug normally would, because this is the slice's one
silent failure. A pooled connection string works — it connects, migrations apply, the health
check goes green — and only misbehaves later under concurrency, stacked pooler on pooler. Every
signal available at the moment of the mistake says success.

The fix is to stop asking the UI and ask the artifact: write `.env.production` first, then
`grep -q -- '-pooler'` it. Added to the REFERENCE with the command. Also corrected there:
pooling defaults **on**, so turning it off is a change to make rather than a default to confirm —
the previous wording ("Turn Connection pooling off") left that ambiguous in the one direction
that costs something.

This also settles how the credential step should be driven. Clipboard → file through a shell
pipe, with a one-word verdict printed, means the string never renders anywhere — so the step is
safe for an agent to run end to end, and does not need handing back to the user the way an
OAuth screen does. Cross-referenced to SKILL.md §2b.

## Confirmed as written

- **`hyperdrive create` declines to edit the config on its own** in a non-interactive shell:
  `🤖 Using fallback value in non-interactive context: no`. The REFERENCE's instruction to copy
  the id across by hand is right, and the comments in `wrangler.jsonc` survive because of it.
- **`--env-file` is required on `create`,** not just on `deploy`, when the login carries several
  accounts — as the REFERENCE says.
- **The `pg` SSL deprecation warning fires on every `migrate:production`** and is noise: the
  migration applies. Still correct not to change the connection string over it.
- **Re-running `migrate:production` is a no-op.** It prints "migrations applied successfully"
  either way, so the evidence is the _absence_ of a `relation "items" already exists` error, not
  the success line. Worth knowing before reading that output as proof of anything.
- **`apps/web` genuinely does not need redeploying.** The deployed page served `ok:db` on its
  next request after the API deploy alone, confirming the service binding resolves to the Worker
  rather than to a version of it.

# The missing CLAUDE.md hunk

Found while building Slice 5 against a workspace carrying 00–04, not while building this slice.

This slice creates `packages/db` and installs `.claude/skills/project-db/SKILL.md`, and said
nothing about either in `CLAUDE.md`. Slices 2 and 4 both amend the package map; 3 did not, so a
project built through this chain ends with a map missing the database layer entirely — and
therefore with no path from `CLAUDE.md` to the operating manual this slice just wrote. The rule
that most needs reaching, `apps/web` never imports this package, is stated only in that skill.

That is the same gap Slice 2 carried until its own entry above, which suggests the pattern
rather than the instance is what to watch: **a slice that creates a package and installs a skill
owes the package map a bullet.** Either way round it is a `docs:check` failure — a project that
adds the line by hand drifts against its own plan, and one that does not ships an incomplete map.

Added as a `## The package map` section before `## Sources`, matching Slices 2 and 4 in placement
and shape. The hunk anchors on the `packages/config` line, which Slice 0's heredoc writes last
and every later slice shares; `docs:check` composes hunks in slice order, so this one lands above
Slice 5's `packages/email` bullet without either needing to know about the other.

Nothing else in this slice was re-verified — it was not rebuilt, only read.
