## The stale-worker warning was too weak, and this is the correction that matters

The REFERENCE warned that a stale `wrangler dev` keeps 8787 and pushes the new one to 8788, and
told you to read the "Ready on" line. That warning is true and it is not sufficient.

Here the new Worker **did** take 8787, `curl :8787/api/auth/get-session` answered `200`, and the
browser round still failed with `Cannot query field "viewer" on type "Query"`. `apps/web`'s
`API` binding is a service binding: it resolves by service *name* through wrangler's dev
registry, not by port, and a stale supervising node process from an earlier session still owned
the registry entry for that name. Preview was talking to a Worker that predated the auth routes
while every port-level check looked correct.

Two further findings from recovering:

- **The preview log's `env.API (cc4-test-graphql) Worker local [connected]` is not evidence.**
  It says *a* local worker answered. It does not say which one, and it printed `[connected]`
  throughout the failure.
- **Killing the stale process does not fall through to the live Worker.** The name goes
  unregistered and the proxy answers `503 Worker "cc4-test-graphql" not found` until
  `apps/graphql`'s `pnpm dev` is restarted — so recovery is kill, restart API, restart preview,
  in that order.

The REFERENCE now prescribes probing the proxy and the direct port together and requiring `200`
from both, which is the check that actually distinguishes the two Workers.

### Two production checks that need no credential, added to the REFERENCE

The slice already forbids reading the token out of `verification` to skip the inbox — correctly,
since it is the operator's credential. What it did not offer was anything to put in that gap, so
the production gate had a hole exactly where its riskiest behaviour lives. Two checks fill it:

- **Count rows instead of reading them.** After a link request production held `verification` 1
  and `user` / `session` / `account` 0. One query proves the secret, the migration, Hyperdrive
  and all four tables, *and* the two properties the gate cares about — a link request issues no
  session and creates no account. The `user` row appears only when the link is followed. Counts
  are not credentials.
- **Drive the verify route with a deliberately invalid token.** It answered `302` with
  `location: <web origin>/?error=INVALID_TOKEN`. That single response proves the two failures
  most likely to be production-only: `redirect: "manual"` surviving to the deployed proxy (a
  followed redirect returns Yoga's landing page as `200`), and `BETTER_AUTH_URL` naming the web
  origin rather than the API Worker. The reference called the redirect the test that "guards the
  whole product" and then had no way to check it in production; now it does.

The general lesson: **when a rule forbids touching a credential, the gate owes a mechanism check
that does not need one.** A prohibition with no substitute turns into someone quietly breaking
the rule, or into a row nobody checks.
