# Preflight, and the probe that leaked a live key

## The finding

`stripe config --list` writes `pk_live_…` and `account_id` straight to the terminal. Stripe
redacts its live *secret* key in that output, which is exactly what makes the command look safe
to run and is why it was reached for as a probe in the first place.

SKILL.md §6 has always said never echo a secret, but §6 governs the production gate — a preflight
probe runs long before any rule there applies. The general lesson is now in §2b: **probe for
presence, never print content.** The specific form for this slice:

```bash
stripe config --list | grep -q account_id    # exit code only
```

## What changed

A `## Preflight` block with that probe and `stripe --version`, and a `USER-SETUP.md` carrying the
account, the keys, the CLI and the card.

**The two prerequisites block different rounds.** The CLI blocks Round 1, because the local gate
forwards webhooks through `stripe listen`; the account blocks both.

Two claims moved into the user's file and are worth restating here, since both cost time when
missed. This slice needs **both** the `sk_test_` and the `pk_test_` key, unlike a hosted
integration — embedded Checkout runs in the browser, so the publishable key is load-bearing. And
`stripe login` must link the **same sandbox the keys came from**: forwarding from one account to
a Worker holding another's key fails signature verification with an error that names neither
account.

The CLI install line was corrected while moving. It read `npm install -g @stripe/cli`; the
user's file now gives `brew install stripe/stripe-cli/stripe` on macOS and points at
docs.stripe.com/stripe-cli for the Linux package and Windows build.

## The card row is unchanged, and still the user's

`4242 4242 4242 4242` is a documented public constant, and the reason this step is handed over
is not policy: Checkout's fields live in a cross-origin `js.stripe.com` iframe and never reach
the accessibility tree, so the agent cannot type into them. That distinction is worth preserving
against a future reading of "preflight is more proactive now" as licence to try.

  `` mail keys and `BETTER_AUTH_URL`. `` but the line continues

- `project-auth`, the link rule. Slice 06 writes **"The link is built from `baseURL`**, so it

## Adaptive pricing makes the amount row wrong as written

The local gate asked for `$19.00` in the iframe. What renders on an account whose country is
not the US is a **Choose currency** selector with the local currency preselected — `SGD 25.02`
beside `US$19.00`, rate underneath — because `adaptive_pricing.enabled` is `true` by default on
new accounts. The session is unaffected: `amount_total` is still the `1900` USD cents the
resolver sends. The row now reads "one line item; `US$19.00` — possibly beside a local
currency", with a paragraph explaining it and naming
`adaptive_pricing: { enabled: false }` as the opt-out.

## `stripe events resend` works locally, so idempotency need not wait for production

The local table's row eight said only "the same event replayed from the Stripe CLI" and gave no
command; the concrete replay was described as a production-only check. With `stripe listen`
running, `stripe events resend <evt_…>` re-delivers through the forwarder with no
`--webhook-endpoint` argument — a second `200`, still one row, `received_at` unchanged. That is
the same evidence the production gate's resend row collects, available a round earlier and
against the CLI's real signing secret. Row rewritten as the command, with the read-the-timestamp
reasoning moved up from the production section.

## The preview latency figure was one machine stated as a constant

"measured at roughly five under workerd" — it was ~17s on this run, with the form mounting
correctly. A number that varies by machine invites chasing a working page. Replaced with a
range and, more usefully, with the discriminator: the console carries only Stripe's
informational "You may test your Stripe.js integration over HTTP" warning when the delay is
just latency, and an actual error when it is not.

# Round 2, deployed and gated for the first time

Everything automatable passed. One finding, and it is the kind that wastes an hour.

## Hyperdrive's read cache makes a working webhook look broken

The production gate reads `stripeEvents`, delivers an event, and reads again. Hyperdrive's
query cache is enabled by default with a 60-second TTL, so the second read is served from the
first: an empty list, for up to a minute, after a delivery that returned `200`.

That is indistinguishable from a webhook that verified and then wrote nothing — and the failure
table's `200, but the row never appears` row pointed straight at the insert, which was innocent.
`wrangler tail` settled it in one line: `POST /stripe/webhook`, `"outcome":"ok"`, status `200`,
no `console.error`. The row had been there the whole time; waiting out the TTL showed it.

Two corrections: a paragraph before the resend row explaining the cache and naming `wrangler
tail` as the faster confirmation, and the failure-table row rewritten to suspect the cache
first. Deliberately **not** recommending `caching: { disabled: true }` as the default — the
pooling and caching are why Hyperdrive is in the stack, and turning the cache off to make a gate
read faster is optimising the wrong thing. It is named as an option for projects where a stale
read actually matters.

Worth stating plainly because it generalises past this slice: **any gate that proves a write by
reading it back through Hyperdrive has this problem**, not just this one. A read-back is not
evidence of a write until the cache is accounted for.

## Confirmed against production

- `stripe events resend <evt> --webhook-endpoint <we>` against the deployed endpoint: still one
  row, `received_at` unchanged. Idempotency holds against the real endpoint secret, not just
  the test double.
- `POST` with no signature and `GET` to the public URL: `400` and `405`, nothing written.
- `ui_mode` took: the form renders on the project's own web origin, never `checkout.stripe.com`.
- API bundle after adding `stripe`: **5236 KiB raw / 941 KiB gzipped**, against Cloudflare's
  3 MiB gzipped ceiling. Room, but the SDK is the largest single dependency in the Worker — the
  next slice to add one should still read the dry-run figure.
- The warning about `stripe trigger` fanning out to every subscribed endpoint on the account is
  real: this account already carried an endpoint for an unrelated project, which received the
  same test events. Harmless in test mode, and worth knowing before wondering why another
  project grew rows.
