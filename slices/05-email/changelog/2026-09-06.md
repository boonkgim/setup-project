# Preflight, and the Resend account steps

## What changed

A `## Preflight` block, and a `USER-SETUP.md` holding what only a person can do.

The probe here is the weakest kind and honest about it: `grep -l RESEND_API_KEY
apps/graphql/.env*` finds a key already on this machine but can say nothing about whether an
account exists. No command can. So the account is one of the few things that genuinely reaches
the user as a question — and it blocks **Round 2 only**, which the preflight block states,
because local rendering sends nothing and the whole package is provable without a key.

## Moved out of the REFERENCE

`### 1. Resend account and API key — one time` is now a pointer. The signup, the **Sending
access** scope, and the shared-sender limit live in `USER-SETUP.md`.

That limit is the reason this section is worth keeping intact rather than compressing to a
signup link: `onboarding@resend.dev` delivers **only to the address the account was created
with**, and every other recipient is rejected at Resend rather than by this code. A user who
does not read that sentence reads a rejection whose cause is nowhere in the repo. It decides
what goes in `MAIL_TEST_RECIPIENTS`, which is the value the production gate refuses a send
without.

The `wrangler secret put` step stays available to the user as an interactive command but is no
longer described as theirs alone — a Resend key is not a live payment credential, and SKILL.md
§6 already governs when the agent may move a secret down a pipe without printing it.

# Round 1 corrections: the CLAUDE.md hunk, the WorkerEnv claim, the key placeholder

A build of this slice against a workspace already carrying 00–04. Four corrections to the
REFERENCE, one of which had made `pnpm docs:check` fail at the end of every previous run.

## `pnpm docs:check` could never pass — the CLAUDE.md hunk anchored on prose

The hunk read:

```
 Worker; SDL modules colocated with resolvers under src/schema), packages/db (Drizzle
-schema + client), packages/config (shared tsconfig).
```

That sentence does not exist and cannot exist. Slice 0's heredoc writes `CLAUDE.md` as a
**bullet list**, one entry per package, and Slices 2, 3 and 4 add bullets to it — so the
composed baseline `docs:check` builds is a list, and a hunk whose context is a paragraph
matches nothing. The failure is silent right up to the final gate row, then reports
`CLAUDE.md — contents differ from the doc` with no hint that the doc is what is wrong.

Rewritten to add a bullet above the `packages/config` line, which is the anchor every later
slice shares. The general lesson is the one already learned in Slice 2's 2026-09-06 entry and
apparently not propagated: **a hunk against a shared file has to be written against what the
chain's own heredoc produces**, not against a paraphrase of it.

## `WorkerEnv` does not carry all three mail keys

The REFERENCE asserted that `createMailer(ctx)` typechecks "because `MailEnv` is declared
structurally and `WorkerEnv` now carries all three keys". It carries two. `cf-typegen`
generates `WorkerEnv` from `wrangler.jsonc` plus the env file, and `RESEND_API_KEY` is in
neither — it is a secret, so nothing wrangler reads knows its name. Verified by running
`cf-typegen` and reading the emitted interface: `HYPERDRIVE`, `CORS_ORIGINS`, `APP_ENV`,
`MAIL_FROM`, `MAIL_TRANSPORT`, `MAIL_TEST_RECIPIENTS`, and no key.

The code was right and the reasoning was wrong, which is the worse of the two failures: the
call compiles because `MailEnv` declares `RESEND_API_KEY?: string`. Corrected in place, with
the consequence stated — a secret cannot be statically proven present, so the `if (!key) throw`
is load-bearing rather than defensive, and widening `WorkerEnv` by hand would assert something
false. The same paragraph was added to the `project-email` skill the slice installs, since that
is where the next person meets the question.

## The `RESEND_API_KEY` placeholder defeated this slice's own preflight probe

The `.env.development` fragment shipped `RESEND_API_KEY="re_..."` uncommented. With
`MAIL_TRANSPORT=log` nothing reads it, so it is inert — but it answers
`grep -l RESEND_API_KEY apps/graphql/.env*`, which is the preflight probe this same REFERENCE
defines, and would report a key present on a machine that has none. Commented out. A probe
that a slice's own scaffolding can satisfy is not a probe.

## The gate row named an absolute test count

`Tests 32 passed — 22 + email 7 + graphql 3`. The 22 is slice 4's total in the repo this
slice was last built in; the repo built today ended slice 4 at 20, because its `packages/db`
has an integration test and no unit test, and `passWithNoTests` makes that green and invisible.

Replaced with the delta — **+7 email, +3 graphql** — plus a note on why an absolute is the
wrong thing for a REFERENCE to assert. §7's test applies literally here: "22" is not true in a
repo with a different name and owner, so it belonged in the project's own slice file, which is
where it now is.

## Confirmed unchanged

- `react-email` 6.9.3, `resend` 6.26.0, `@react-email/ui` 6.9.3 — none deprecated.
  `@react-email/components` 1.0.12 still carries "Package no longer supported", so the
  one-package install and the warning it teaches you to read are both still current.
- `react-email` exports a single root entry and depends on `@react-email/render >=2.1.0`; the

- `email dev` still takes `--dir` and `--port`, still defaults to 3000.
- **The bundle figures held exactly**: 2576.23 KiB raw, 520.85 KiB gzipped, against the

- `pnpm lint` reporting `6 successful` (4 lint + 2 codegen) was right.

# `USER-SETUP.md` §2 told you to use a key it never told you how to get

Raised by the user mid-build, looking at the handover message: the instruction was
`pnpm wrangler secret put RESEND_API_KEY`, and nothing anywhere said where `RESEND_API_KEY`
comes from. §2 read, in full, "From the dashboard, create a key and give it **Sending access** —
not full access."

That is a step only for a reader who already knows the Resend dashboard. It names no URL, no
button, and — the omission that actually costs something — does not say that **the key is
displayed once and cannot be viewed again**. Resend's own docs are explicit ("You cannot view or
edit an API key value after it has been created"), so a reader who closes the dialog before
copying has to delete the key and create another. A setup file whose job is to be followed by
someone who has not done this before must say that *before* the click, not after.

Rewritten as six numbered steps: the page (`resend.com/api-keys`), **Create API Key**, a name,
**Sending access** with the reason (Full access also reads contacts and manages domains and
other keys; this Worker only calls `emails.send`), the domain field left unrestricted while
`MAIL_FROM` is still the shared sender, and the one-shot reveal called out with the `re_` prefix.
Added two non-revealing ways to confirm it landed, and made explicit which half of the job is
negotiable: an agent may *paste* a key it is handed, but cannot *fetch* one, because reading it
off the dashboard means rendering it on screen.

Generalised into SKILL.md's description of `USER-SETUP.md`, since nothing about this is specific
to Resend: **name the page, name the button, and flag anything shown only once.** The
one-shot-value case is the sharp one — every other vague instruction wastes a minute, and that
one destroys a credential.

# Round 2 (production): the dashboard owns three rows the gate gave to a human

First real run of this slice's production gate, with a live Resend account.

## Everything the gate asserted, held

`wrangler secret put` uploaded against `cc4-test-graphql`; `secret list` reported
`RESEND_API_KEY` / `secret_text` without revealing it. The deploy's bundle came in at
**2576.23 KiB raw, 520.85 KiB gzipped** — the REFERENCE's "roughly 2576 KiB and 521 KiB",
unchanged across a `react-email` minor. `sendTestEmail` returned `true` for the allowlisted
address and `Recipient is not in MAIL_TEST_RECIPIENTS` for one off the list, with no second
message created.

## The manual round was three-quarters unnecessary

The gate handed the user four rows: does it arrive, is there a `text/plain` part, does the
refusal send nothing, does it look right. **Three of them are in Resend's own dashboard**, and
nobody had checked because the round was labelled manual and manual rounds do not get driven.

- **Arrival** — the message list shows `Delivered`, and the events timeline carries separate
  `Sent` and `Delivered` timestamps. That is the receiving MX accepting it, which is strictly
  more than the "Resend accepted it" the old wording said `true` was worth.
- **The plain-text part** — the **Raw** tab is the submitted JSON, with `"text"` populated
  beside `"html"` and `"last_event": "delivered"`. The **Insights** tab asserts it independently:
  *Include plain text version* ✓.
- **The refusal** — the absence of a second row, same counting rule as the local round.

Only "does it look right in a client" survives as a person's job, and it genuinely does: a
dashboard preview is not an inbox, and rendering is the thing inboxes disagree about. The gate
now says so, with a table naming where each row's evidence actually lives.

The general lesson is the one SKILL.md §6 already states and this slice was not obeying: **a row
is manual only if no tool can reach the evidence.** "Check your inbox" sounds unautomatable and
mostly is not — the sending provider logs delivery, and its log is better evidence than a person
squinting at a message, because it distinguishes accepted from delivered.

## Two Insights warnings that are not defects

`Ensure link URLs match sending domain` and `Use a subdomain` both fire on every send this slice
makes, because the link is `https://<project>.example/...` and the sender is the shared
`onboarding@resend.dev`. Both are placeholders this slice picks on purpose, and both are already
in `Leaves behind` — this is a third party restating them. Recorded in the REFERENCE so the next
build does not chase them as regressions.

## The key never had to reach the user's hands

`USER-SETUP.md` said the copy was the user's either way, "because reading it off the dashboard
means rendering it on screen". That turned out to be false: Resend renders a new key in an
`<input type="password">` with a **Copy to clipboard** button, so the value can go dashboard →
clipboard → `wrangler secret put` without ever being displayed or entering any transcript. Driven
that way here — clipboard asserted against `re_*` before piping, only a length and a prefix
verdict printed, clipboard cleared afterwards. Exactly slice 3's connection-string pattern.

Corrected in both `USER-SETUP.md` and the REFERENCE's step 3. What still belongs to the user is
**authorising** the key's creation, because that makes a real credential in their name — not the
typing, which was never the sensitive part.
