# Preflight, and the split between agent steps and user steps

Skill-level change: SKILL.md, the catalog, and the shape of a slice directory. Per-slice
consequences are recorded in each slice's own changelog.

## The defect

SKILL.md §2 said: *"If the slice needs an account the user does not have (Cloudflare, Neon,
Resend, Stripe), say so **now**."* It presupposed knowledge of something it never said how to
obtain, and the only way to close that gap mid-run was to ask. So a run would open by putting a
multiple-choice question to the user — *are you logged in to Cloudflare? does that login carry
more than one account?* — whose entire answer `wrangler whoami` prints in one call, account ids
included.

The command was not even missing from the skill. It sat in slice 01's REFERENCE as an inline
comment at the point `.env.production` gets written, roughly step fifteen. The detection existed
at step fifteen while the decision to ask happened at step two.

§3 already carried the right instinct — *check reality rather than the reference* — but only
ever pointed outward, at pins, flags and vendor docs. Nothing pointed at the machine the run is
happening on.

## What changed

**New §2b, "Preflight: settle what you can settle",** between reading the reference and
researching the world. Its rule: *a fact a command on this machine can obtain is never a
question.* It carries the two rules that govern a probe and the instruction to hand over setup
steps when one fails — and no probe commands, for the reason below. The loop line at the top of
SKILL.md gains `preflight` after `reference`.

**Probes live in the slice, not in SKILL.md.** The first draft of §2b held two central tables —
every probe, and a remedy for every missing tool. That is precisely the shared bibliography §7
threw out, rebuilt one file over: duplicated into the slices that needed it, and stranded in a
file no step tells you to open. A project stopping at 02 should never be told how to install the
Stripe CLI. Each slice's `REFERENCE.md` now opens with a `## Preflight` block naming only its
own probes.

**New per-slice `USER-SETUP.md`** — accounts, browser logins and OS-level installs, written for
a person, each section tagged with the round it unblocks. `REFERENCE.md` becomes strictly what
an agent can execute; where a step needs a human it is a one-line pointer. Only slices that need
something from a person have the file (00, 01, 03, 05, 07): its absence states that the slice
needs nothing, so there are no placeholder files. It is never rendered into a project, which
keeps §4's invariant that `docs/setup/` holds slice files only.

**Round tagging.** A missing prerequisite no longer stops a slice by default. A runtime blocks
everything, Docker blocks Round 1, and an account usually blocks Round 2 alone — so the local
half is built, gated and committed with Round 2 reported as deferred.

**The catalog's accounts table gains a `Probe` column,** and its instruction flips from "Ask
about these" to "Probe for these; do not ask". Its heading already read *first* required at, and
that turns out to be load-bearing: every need lands at exactly one slice, so the duplication a
central setup file would have avoided barely exists. A later slice re-probes rather than
re-running setup.

## Two probes worth keeping

`stripe config --list` prints `pk_live_…` and account ids straight to the terminal — Stripe
redacts only its live *secret*. SKILL.md §6 has always said never echo a secret; nothing applied
that to a probe, which runs earlier than any rule §6 governs. Probes now test for presence and
read exit codes: `stripe config --list | grep -q account_id`.

`wrangler whoami` exits non-zero when logged out. That is the probe's answer, not a failure to
retry — stated in §2b because the retry instinct is strong and wrong here.

## What stayed

The §0 catalog confirmation, Round 3's manual handoff, and the prohibition on handling live
credentials. None of those is a fact a probe could settle; they are decisions, human perception,
and blast radius respectively. Making the skill more proactive about facts is not a licence to
decide things that were never the agent's to decide.

## A gap this opens

`SKILL.md` has no changelog of its own — §7 gives one to every slice and none to the method. This
file is that changelog, newly created, and the convention it sets is: skill-level changes here,
slice-level changes in the slice. It has one property worth watching, being the only append-only
record in the skill that is not scoped to a slice, which is the shape §7 warns about.

# Project skills: named `project-<layer>`, and committed

Two defects found while building a project through slice 02. Both are cross-slice rules rather
than one slice's procedure, which is why they are here and not in a slice changelog.

## The manuals were being named too generically

Slices 02 through 07 each install their layer's operating manual, and they had picked names
independently: `graphql`, `web`, `email`, `auth`, `payments`, plus `code-db` and `code-ui`, which
did not match the others. Two problems, one of them silent.

Inconsistency is the visible one. The collision is the one that costs something: `web`, `auth`,
`db` and `payments` are generic enough to clash with a skill in `~/.claude/skills/` or a plugin,
and nothing announces the clash — the wrong manual simply loads, and an agent then follows
another project's rules for touching this one's schema.

Every installed manual is now **`project-<layer>`**, with the directory and the `name:` in its
frontmatter kept in agreement: `project-graphql`, `project-web`, `project-db`, `project-email`,
`project-auth`, `project-payments`, `project-ui`. `code-db` and `code-ui` are folded into the
same shape. `assets/code-ui-SKILL.md` is renamed to `assets/project-ui-SKILL.md` so the source
file matches what it installs as. Slice 03, which previously told the reader to match whatever
the project already called its skills, now states the rule instead — an ad-hoc "match the
neighbours" instruction is what let the names diverge in the first place.

The cross-slice `diff` hunks in slices 06 and 07 anchor on these paths, so they moved with them.
A fixed prefix was chosen over the project's own name (`__PROJECT__-graphql`) precisely to keep
those anchors constant: the renderer could substitute it, but every patch context would then be
project-specific for no gain.

## The manuals were not being committed

`.claude/skills/setup-project` is a symlink when the skill is vendored into a project, and git
stores a symlink as its target string — so committing it writes one machine's absolute directory
layout into the repo. The obvious defence is to ignore `.claude/skills/`, and a project that had
done that hit the consequence at slice 02: the manual the slice had just written was ignored
along with the symlink.

It fails silently and late, which is what makes it worth a permanent warning rather than a note.
The slice committed a `CLAUDE.md` **pointing at** `.claude/skills/project-graphql/SKILL.md` while
the file itself was untracked, so a fresh clone received the pointer and not the manual. Nor did
`docs:check` catch it: it reported the file as `not built yet` — a false negative for a slice
that _is_ built, from the one check whose whole job is noticing that the plan and the repo
disagree. Verified by moving the file aside and re-running.

Slice 00 now says to ignore the **exact symlink path**, never the directory, and states why the
manuals are project source: referenced from `CLAUDE.md`, compared by `docs:check`, and useless to
anyone who clones without them.
