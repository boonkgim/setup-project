# Preflight, and the split between agent steps and user steps

Skill-level change: SKILL.md, the catalog, and the shape of a slice directory. Per-slice
consequences are recorded in each slice's own changelog.

## The defect

SKILL.md §2 said: _"If the slice needs an account the user does not have (Cloudflare, Neon,
Resend, Stripe), say so **now**."_ It presupposed knowledge of something it never said how to
obtain, and the only way to close that gap mid-run was to ask. So a run would open by putting a
multiple-choice question to the user — _are you logged in to Cloudflare? does that login carry
more than one account?_ — whose entire answer `wrangler whoami` prints in one call, account ids
included.

The command was not even missing from the skill. It sat in slice 01's REFERENCE as an inline
comment at the point `.env.production` gets written, roughly step fifteen. The detection existed
at step fifteen while the decision to ask happened at step two.

§3 already carried the right instinct — _check reality rather than the reference_ — but only
ever pointed outward, at pins, flags and vendor docs. Nothing pointed at the machine the run is
happening on.

## What changed

**New §2b, "Preflight: settle what you can settle",** between reading the reference and
researching the world. Its rule: _a fact a command on this machine can obtain is never a
question._ It carries the two rules that govern a probe and the instruction to hand over setup
steps when one fails — and no probe commands, for the reason below. The loop line at the top of
SKILL.md gains `preflight` after `reference`.

**Probes live in the slice, not in SKILL.md.** The first draft of §2b held two central tables —
every probe, and a remedy for every missing tool. That is precisely the shared bibliography §7
threw out, rebuilt one file over: duplicated into the slices that needed it, and stranded in a
file no step tells you to open. A project stopping at 02 should never be told how to install the
Stripe CLI. Each slice's `REFERENCE.md` now opens with a `## Preflight` block naming only its
own probes.

**New per-slice `USER-SETUP.md`** — accounts, browser logins and OS-level installs, written for
a person, each section tagged with the round it unblocks. `REFERENCE.md` becomes strictly what
an agent can execute; where a step needs a human it is a one-line pointer. Only slices that need
something from a person have the file (00, 01, 03, 05, 07): its absence states that the slice
needs nothing, so there are no placeholder files. It is never rendered into a project, which
keeps §4's invariant that `docs/setup/` holds slice files only.

**Round tagging.** A missing prerequisite no longer stops a slice by default. A runtime blocks
everything, Docker blocks Round 1, and an account usually blocks Round 2 alone — so the local
half is built, gated and committed with Round 2 reported as deferred.

**The catalog's accounts table gains a `Probe` column,** and its instruction flips from "Ask
about these" to "Probe for these; do not ask". Its heading already read _first_ required at, and
that turns out to be load-bearing: every need lands at exactly one slice, so the duplication a
central setup file would have avoided barely exists. A later slice re-probes rather than
re-running setup.

## Two probes worth keeping

`stripe config --list` prints `pk_live_…` and account ids straight to the terminal — Stripe
redacts only its live _secret_. SKILL.md §6 has always said never echo a secret; nothing applied
that to a probe, which runs earlier than any rule §6 governs. Probes now test for presence and
read exit codes: `stripe config --list | grep -q account_id`.

`wrangler whoami` exits non-zero when logged out. That is the probe's answer, not a failure to
retry — stated in §2b because the retry instinct is strong and wrong here.

## What stayed

The §0 catalog confirmation, Round 3's manual handoff, and the prohibition on handling live
credentials. None of those is a fact a probe could settle; they are decisions, human perception,
and blast radius respectively. Making the skill more proactive about facts is not a licence to
decide things that were never the agent's to decide.

## A gap this opens

`SKILL.md` has no changelog of its own — §7 gives one to every slice and none to the method. This
file is that changelog, newly created, and the convention it sets is: skill-level changes here,
slice-level changes in the slice. It has one property worth watching, being the only append-only
record in the skill that is not scoped to a slice, which is the shape §7 warns about.

# Project skills: named `project-<layer>`, and committed

Two defects found while building a project through slice 02. Both are cross-slice rules rather
than one slice's procedure, which is why they are here and not in a slice changelog.

## The manuals were being named too generically

Slices 02 through 07 each install their layer's operating manual, and they had picked names
independently: `graphql`, `web`, `email`, `auth`, `payments`, plus `code-db` and `code-ui`, which
did not match the others. Two problems, one of them silent.

Inconsistency is the visible one. The collision is the one that costs something: `web`, `auth`,
`db` and `payments` are generic enough to clash with a skill in `~/.claude/skills/` or a plugin,
and nothing announces the clash — the wrong manual simply loads, and an agent then follows
another project's rules for touching this one's schema.

Every installed manual is now **`project-<layer>`**, with the directory and the `name:` in its
frontmatter kept in agreement: `project-graphql`, `project-web`, `project-db`, `project-email`,
`project-auth`, `project-payments`, `project-ui`. `code-db` and `code-ui` are folded into the
same shape. `assets/code-ui-SKILL.md` is renamed to `assets/project-ui-SKILL.md` so the source
file matches what it installs as. Slice 03, which previously told the reader to match whatever
the project already called its skills, now states the rule instead — an ad-hoc "match the
neighbours" instruction is what let the names diverge in the first place.

The cross-slice `diff` hunks in slices 06 and 07 anchor on these paths, so they moved with them.
A fixed prefix was chosen over the project's own name (`__PROJECT__-graphql`) precisely to keep
those anchors constant: the renderer could substitute it, but every patch context would then be
project-specific for no gain.

## The manuals were not being committed

`.claude/skills/setup-project` is a symlink when the skill is vendored into a project, and git
stores a symlink as its target string — so committing it writes one machine's absolute directory
layout into the repo. The obvious defence is to ignore `.claude/skills/`, and a project that had
done that hit the consequence at slice 02: the manual the slice had just written was ignored
along with the symlink.

It fails silently and late, which is what makes it worth a permanent warning rather than a note.
The slice committed a `CLAUDE.md` **pointing at** `.claude/skills/project-graphql/SKILL.md` while
the file itself was untracked, so a fresh clone received the pointer and not the manual. Nor did
`docs:check` catch it: it reported the file as `not built yet` — a false negative for a slice
that _is_ built, from the one check whose whole job is noticing that the plan and the repo
disagree. Verified by moving the file aside and re-running.

Slice 00 now says to ignore the **exact symlink path**, never the directory, and states why the
manuals are project source: referenced from `CLAUDE.md`, compared by `docs:check`, and useless to
anyone who clones without them.

# Browser setup steps: an offer, not a handoff

Skill-level change: SKILL.md §2b and §6. No slice procedure changed.

## The defect

§2b's handling of a failed probe had exactly one move — hand the user the written steps from
`USER-SETUP.md` — and §6 backed it with a flat reservation: _creating or configuring an account
(Cloudflare, Neon, Resend, Stripe) with credentials only the user holds_ was listed beside
completing an OAuth consent screen as something that "actually requires a human".

Those two are not alike, and merging them cost the user work. A consent screen requires a human
because the grant is _made_ by the click. A signup does not: it requires a human's
**authorisation**, and then a few minutes of clicking a form that the Chrome tooling — driving
the user's own logged-in browser, in their own session, with their own cookies — can do as well
as they can. The skill was inferring "you must do all of it" from "it is yours to decide", which
is a different claim.

The symptom was a run putting a three-option question to the user (_do you have a Neon project?
… no — I'll create one … you create it during the slice_) whose middle option promised nothing
more than a list, in a session where the browser tools were loaded and the console was two
clicks from open.

## What changed

**New §2b subsection, "Offer to drive the browser steps."** Check availability as a fact rather
than asking about it; make one offer naming what you would do and where you would stop; act on an
explicit yes. Four handover points are enumerated and each **ends the turn** rather than pausing
it — the user's own credentials, a code proving possession, a consent screen, and anything
attaching a payment method or leaving a free tier. Values read off a page fall under §6's
never-echo rule unchanged: a connection string or key goes browser → gitignored env file, never
into a message or a retained screenshot, and a step that cannot move a secret without rendering
it reverts to the user. Declined or unavailable falls back to the written steps, under the same
stop-after-2–3-failures rule that governs every other browser task.

**§6 Round 2's reservation is narrowed** to point at that mechanism: consent screens and typed
credentials stay human; account _creation_ is the user's to authorise and the agent's to click.

**§2b's residue-question paragraph** now says that when the answer is "create it", the question
takes the shape of the offer rather than handing back the whole errand.

## The line this walks

The first entry in this file recorded, under _What stayed_, that being more proactive about facts
is "not a licence to decide things that were never the agent's to decide". That still holds and
is the reason the offer is an offer: authorisation did not move. What moved is the assumption
that authorising and executing are the same act. The four handover points are where they
genuinely are the same act, and those are exactly the points the agent stops at.

Worth watching: an agent that can click a signup can also click past a pricing tier. "Anything
that leaves a free tier" is listed as a handover point for that reason, not as a courtesy.

# A slice changelog was overwritten, not appended

Recorded because the rule it broke already existed and did not prevent it.

§7 says a slice changelog is "a **new file** named for the date, never an edit to an existing
one... Same day, second change: append to that day's file." Building slice 3 produced exactly
that second change, and the agent wrote it with `cat > …/2026-09-06.md`, destroying an entry
made earlier the same day about that slice's preflight and its Neon user-setup steps. It was
recovered from `git show HEAD:<path>` and the new material appended beneath it.

The rule was correct and stated; what was missing is that nothing about `>` announces it is
destroying something. Every other write in a slice is a fresh file or a targeted replacement,
so the one file in the skill with append-only semantics is also the one written with the same
reflex as all the others. Two guards worth applying, in order of reliability:

- **`cat >> …` for a changelog, always** — the file either exists (append, correct) or does not
  (created, also correct). `>` is never right for one of these.
- **Check before writing**: if today's file exists, the change being recorded is a second one,
  which is itself worth knowing before writing the entry.

Left as a note rather than a mechanism, since the skill has no script that writes changelogs.
The general shape is worth naming though: an append-only record kept in a directory where every
other file is freely rewritten will be rewritten eventually, and being right about the rule in
prose is not the same as being safe.

## Appended later the same day: a changelog file was truncated by `cat >`

While building slice 5, an agent reconciling slice 3 wrote
`slices/03-database/changelog/2026-09-06.md` with a `cat >` heredoc without listing the path
first. It already held that morning's entry. The write succeeded silently and replaced it.

Recovered in full from `git show HEAD:<path>` and re-appended to, so the committed content was
never at risk — but the agent had first concluded the loss was permanent, having run
`git rev-parse` one directory too high: this skill is its own repository, nested inside a parent
directory that is not one. **A negative `git` answer is only as good as the directory it was
asked in.** `git -C <the file's own directory> rev-parse --show-toplevel` is the question that
does not depend on guessing where the boundary is.

§7 already said the right thing — "a **new file** named for the date, never an edit to an
existing one … Same day, second change: append to that day's file" — and it was read as guidance
about *intent* (don't rewrite history) rather than about the *command* (don't use a truncating
write on a path you have not listed). It is now stated as a mechanic, because the failure is
silent: `cat >` on an existing changelog succeeds, prints nothing, and looks identical to
creating one.

The general lesson beyond this skill: **an append-only record needs an append-only write.** A
reconcile step that can only add is safe to automate; one that can truncate has to list the file
first, every time.

## `install-plan.mjs` — `--force` was scoped to the whole prerequisite closure

`--force` overwrote every slice file the run touched, including the ones the prerequisite
closure added rather than the ones asked for. Installing slice 06 with `--force` into a repo
built through 05 therefore regenerated `00`–`05` from the reference, destroying five slices'
execution records — and destroying them *silently*, because the files still exist and still
look like plans. The loss is only visible in `git diff`.

The flag now overwrites a slice file only when its id was named on `--slices`/`--through`.
Assets stay unscoped: they are shipped files, not a build log.

The general rule this is an instance of: **a flag that means "yes, overwrite the thing I named"
must not also mean "and everything reached to get there."** The closure exists so prerequisites
get *installed* when missing, which is the opposite of a licence to rewrite them when present.

The `Left alone` hint changed with it — it used to say "pass `--force` to overwrite", which is
now false for a slice that was not named. It says "name it on `--slices` with `--force`".

## `install-plan.mjs` — the slice-06 asset was copied under a name that does not exist

The script read `assets/code-ui-SKILL.md`; the file on disk is `assets/project-ui-SKILL.md`,
which is also the name SKILL.md and slice 06's REFERENCE both use. Installing slice 06 crashed
with `ENOENT` — after the slice files were already written, so the run looked half-done. Fixed
to the real name.

Worth noting how it survived: the mismatch is only reachable by installing slice 06, which is
the last build slice most repos have not reached, and nothing else in the skill references the
wrong name. A path that appears in exactly one code branch and no document is one only
execution can check.
